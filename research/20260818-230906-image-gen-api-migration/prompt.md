# このリポジトリについて

これは Claude Code（Anthropic製CLIエージェント）向けの「ハーネス」を管理するリポジトリである。ハーネスとは、AIエージェントが参照する知識ファイル群の総称で、`.claude/skills/<スキル名>/SKILL.md` の形式でスキルが定義される。SKILL.md はオーナー（人間の利用者）からの特定の指示（例：「画像を生成して」）をトリガーに、AIエージェントが呼び出す手順書であり、Markdown内にBashコマンド例などが直接書かれ、AIエージェントがそれを解釈して実行する。

このリポジトリには `image-gen` という名前のスキルがあり、現在は以下の内容で実装されている（`.claude/skills/image-gen/SKILL.md` の全文）。

```markdown
---
name: image-gen
description: codexを用いて画像を生成し、リポジトリ内の指定パスにコピーする。「画像を生成して」「画像を作って」などの指示で使う。
---

## ルール

- `codex exec` は `Bash` ツールで直接実行する（同期実行）。`TaskCreate` による非同期実行は禁止
- Bashツールの `timeout` パラメータに最低 **600000ms（10分）** を指定する（デフォルト2分ではタイムアウトする）
- codexは画像生成のみを担当する（セキュリティのため最小権限）
- 生成画像のリポジトリへの移動は claude code の責務
- 出力先パスがオーナーから指定されていない場合は確認する
- リファレンス画像（キャラクター設定画・既存の生成物など）がある場合、必ず `codex exec` の `--image` オプションで渡す。テキストプロンプトだけで一貫性を保とうとしない
  - `-i, --image <FILE>...` は複数値を取れるオプションのため、`--image path1 --image path2 "<prompt>"` のように書くと、プロンプト文字列まで `--image` の値として貪欲に読み込まれ、プロンプトが渡らずに失敗する
  - 必ず画像パスをカンマ区切りでまとめ、`--` でプロンプトと明示的に区切ること：`--image path1,path2 -- "<PROMPT>"`
  - プロンプト内で各画像の役割を明示する（例：「Image 1は○○のキャラクター設定画、Image 2は…」）

## 手順

1. codex で画像生成を実行し、出力をファイルに保存する（`<PROMPT>` を実際の生成指示に置き換える）

（`codex exec --model gpt-5.5 --sandbox read-only --ephemeral --skip-git-repo-check --config 'approval_policy="never"' "<PROMPT>"` を実行し、生成された画像を `~/.codex/generated_images/<セッションID>/*.png` から取得する、という内容）

2. 生成画像をリポジトリ内の指定パスにコピーする

## エラー時の対応

codex コマンドが失敗した場合（認証エラー・コマンド不在・その他）、代替手段で自己解決しない。オーナーにエラー内容を報告し、指示を仰ぐ。
```

つまり現状は、ローカルにインストール・認証済みの `codex` CLI（OpenAI Codex CLI）をサブプロセスとして呼び出し、その内部で画像生成モデルを呼ばせている。`codex` 自身の認証情報（APIキーやOAuthトークン）は codex のログイン設定（`~/.codex/` 配下など）に保存されており、SKILL.md や AIエージェントは一切キーを扱っていない。

このリポジトリのプロジェクトルール（`CLAUDE.md`）には以下の制約がある。

- 「環境変数の参照禁止。存在確認も禁止」— AIエージェント（Claude Code）は、作業中に `echo $FOO` のようなコマンドで環境変数を参照したり、変数の存在確認をしたりしてはならない、というルールである。
- ハーネス（SKILL.md等）への記述は、オーナーが明示的に指示した内容のみとする。AIエージェント自身の推測や提案を書き込んではならない。

このスキルを、`codex` コマンドのサブプロセス呼び出し方式ではなく、画像生成プロバイダのAPIを直接HTTPリクエスト（curl等）で呼び出す方式に移行したい、というのがオーナーの要望である。

# 問い

Claude Code の SKILL.md（Bashツールでcurl等のコマンドを実行する形式）から、画像生成AI（例：OpenAIのImages API、Google GeminiのImage生成API/Imagen等）をAPI経由で直接呼び出して画像を生成する場合の、実現方法を明らかにせよ。具体的には以下を含めること。

1. 主要な画像生成APIプロバイダ（OpenAI、Google Gemini/Imagen、その他広く使われているもの）それぞれについて、2026年8月時点の最新の画像生成モデル・エンドポイント・リクエスト形式・認証方式（APIキーをどのHTTPヘッダーやパラメータで渡すか）・レスポンス形式（画像データがBase64で返るのか、URLで返るのか）・課金体系（1枚あたりの価格帯や課金単位）を整理する。
2. それぞれのAPIについて、`curl` コマンドでリクエストを送り、レスポンスから画像ファイルを復元してローカルディスクに保存するまでの、具体的なコマンド例（ヘッダー・ボディの中身を含む）を示す。
3. 複数の参照画像（リファレンス画像）を入力として渡して画像編集・合成を行う機能（image-to-image / image editing）が各APIに存在するか、存在する場合はそのリクエスト方法（multipart/form-data か JSON か、Base64エンコードが必要かなど）を明らかにする。
4. シェルスクリプトやCLIコマンドの実行環境において、APIキーのような秘密情報をコマンドライン上の環境変数（`export FOO=xxx` して `$FOO` を参照する方式）を一切使わずに安全にAPIリクエストへ渡す一般的な方法にはどのようなものがあるか（例：秘密情報を平文で書いたファイルをコマンドの引数やstdin経由で読み込ませる、OSのキーチェーン/シークレットマネージャーを使う、設定ファイルに直書きする、等）を、それぞれの利点・欠点とともに整理する。
5. 上記の画像生成API呼び出しにおいて、レートリミットやエラーレスポンス（認証エラー、クォータ超過等）の一般的な形式や、リトライ時の注意点があれば明らかにする。

# 出力要件

- 日本語で記述すること。
- 前提知識のない読者でも理解できるように、専門用語は簡潔に補足すること。
- 各プロバイダごとに見出しを分け、上記1〜3の情報を整理すること。
- 秘密情報の受け渡し方法（上記4）は独立したセクションとしてまとめ、選択肢を列挙し、それぞれの利点・欠点を記述すること（特定の方法を推奨する必要はない。事実の列挙でよい）。
- 参照した公式ドキュメントのURLをすべて出力の末尾に列挙すること。
- 選択肢の提示や好み・推奨の表明は不要。現状把握できる事実（仕様・価格・手順）のみを記述すること。
